> Execute inline with superpowers:executing-plans; direct Codex only, no delegation, Antigravity or cockpit. Approved spec13/DATA contracts and the user's standing instruction to complete tasks sequentially supply scope/authorization. No new product approval loop or redesign.

**Goal:** Implement the real Feed API, purpose-safe image lifecycle and moderation against the PASS DATA interface before frontend work.

**Architecture:** A new Feed Nest module uses locked shared DTOs, parameterized PostgreSQL transactions and current session/ban/verified/onboarding checks. Reuse existing uploads/sharp/storage and social-pair locking, with a small shared Feed infrastructure module for bounded quotas on configured Redis. Feed/Uploads dependency flow is acyclic: Feed imports exported UploadsService; Uploads imports only Feed infrastructure/plain access helpers, never FeedService.

**Tech stack:** Existing Nest12, pg8/Drizzle, Zod4, ioredis6, sharp0.35, Better Auth, native Jest/ts-jest and Supertest. No dependencies, main migration, credential provisioning or production activation.

## Contracts and behavior

- Consume canonical T38-FEED-DATA exports/migration0027 without rewriting DATA. Public GET feed/post/comments and processed bound image content. All responses, including errors and actor-relative liked state, use private/no-store. Authenticated writes enforce current valid session, verified user, onboarding, current ban and actual ownership. Only current sole website admin can delete another author's content, with explicit reason. Room helper/client name does not grant Feed authority.
- Feed posts sort newest first by immutable(createdAt,id); comments sort chronological by the same tuple within one post. Preserve PostgreSQL microseconds for cursor encoding, validate canonical bounded base64url/strict payload, bind game/type/post scope; edits never promote posts. Strict public nickname/avatar/game projections only. Counts come from DB, likes unique/idempotent, comment counts exclude tombstones/hidden authors; no fake counters, Feed notifications, SMTP, push or socket events.
- Feed transaction uses currentSupportActor session-first ordering before content locks, and rechecks authority before commit. Write operations lock the current post FOR UPDATE OF post only; same-post root is then locked and checked undeleted/root-only. Current block decisions coordinate with existing lockSocialPair; viewer filtering follows spec's one-way blocker preference and does not pretend public posts are private. Never acquire another user's exclusive identity lock or introduce a later moderation mutex that could deadlock BAN session drain.
- Retry keys use actual per-author unique rows and canonical payload comparison; changed retries return409. Likes use existing composite relation and current state. Post/comment deletion is idempotent after authority checks, retains original source/audit, hides all post descendants/assets or returns a real null-body root placeholder with existing replies. No edits/likes/replies to deleted posts or deleted roots.
- Redis quotas use the configured existing service, atomic INCR+TTL, a namespace derived from database identity (owned fixture override), bounded connection/command deadlines and fail closed503 before writes when unavailable. Technical limits per actor/minute:10post creates,30post edits,60comment creates/edits,120like toggles,30deletes,40Feed uploads. Existing report quotas remain unchanged. Bounded unbound Feed drafts prevent unlimited abandoned storage; retries do not create duplicate data. No infinite retries/watch.

## Image integration

- Keep the existing authenticated POST uploads/images route and its one-field multipart bound: conversationId for legacy chat OR purpose FEED_POST, never both. Preserve original chat encryption/context transport. Reuse exact signature, byte, pixel and WebP re-encoding validation before purpose-specific persistence; recheck current Feed actor before committing draft bytes/row. Receipt is durable only after commit; no public draft URL.
- FEED_POST drafts have null conversation and actual uploader; legacy CHAT_IMAGE keeps required context. Chat metadata reads must ignore Feed drafts. Feed publish/patch locks unexpired owned Feed drafts and allows retained images only from the same current post; never another post/private draft/caller URL. Verify processed files exist, consume/copy bindings transactionally, max4 positions. Failed DB/filesystem/network operations return errors and preserve retryable state rather than reporting success.
- Export UploadsService for Feed to read only safe UUID files after Feed row visibility/authority checks. Public content route checks bound image, visible undeleted post and actor block state, holds source protection while reading and rechecks before returning; drafts/private IDs/deleted/unbound paths404. No public cache or arbitrary filename/path.
- Preserve all Feed image bindings (including retained soft-delete/audit storage) in the existing orphan sweep. Expired draft deletion commits before physical unlink; ambiguous failure retains files for safe later sweep. Removing a binding prevents public reads immediately; orphan bytes are cleaned through the existing bounded retention/sweep, never by deleting another active binding. No unsafe recursive filesystem move/delete; fault tests validate exact owned runtime paths.
