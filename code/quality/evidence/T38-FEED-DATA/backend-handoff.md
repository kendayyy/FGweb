# Feed DATA → BE integration obligations

DATA does not activate Feed API, uploads or public assets. Do not enable a Feed client against the old compiled API merely because registry/contracts now describe these routes. Apply migration0027 only to a reviewed disposable/staging target under its owning task; no main migration was authorized here.

- UploadsController currently accepts one multipart field. Feed uses the existing authenticated POST uploads/images with a distinct FEED_POST branch and no conversationId; keep CSRF/session/onboarding/ban, count/byte/signature/pixel/re-encoding bounds. CHAT_IMAGE must retain existing encryption/context behavior. Feed public WebP must never be mistaken for private encrypted chat storage.
- UploadsService's draft/image lookups and filesystem sweep currently know chat attachments. Add purpose-aware draft lookup and include every retained feed_post_images binding in object retention before enabling Feed writes. Do not delete a bound Feed asset as an orphan. Conversely, removed/expired drafts and images must not remain publicly readable. Clean physical objects only with safe transactional/durable retry handling; never unlink a shared/rebound object before commit.
- Finalize at most four unique unexpired FEED_POST drafts belonging to the actual post author. Lock and consume them inside the post transaction, with retry identity checks. Never claim a private CHAT_IMAGE draft or accept caller URLs/uploader identity. Keep chat attachment metadata/content routes private; the new Feed image content path reads only processed Feed assets bound to a visible undeleted post, never an unbound draft, stale/deleted source or private chat image. Parameterize all IDs and use safe storage keys.
- The same-post comment FK does not enforce root depth or current visibility. Lock the post and optional root; verify the root belongs to that post, has no parent and is not deleted. Enforce current actor/ownership/ban/block policy in each transaction, including races with deletion. A soft-deleted root exposes only a null-body placeholder while existing valid replies remain readable; deleted posts deny all direct post/comment/image reads and writes.
- Use conditional idempotent like PUT/DELETE with the actual unique(post_id,user_id) relation; do not increment counters optimistically or count twice across tabs/retries. Return canonical counts and likedByMe. Do not reorder edited posts by updatedAt; validate/decode cursor payloads and bind filters/post scope before SQL. Apply existing server rate limits.
- ModerationService currently distinguishes USER vs MESSAGE. Implement an explicit exhaustive target switch for FEED_POST/FEED_COMMENT, current target/source ownership and sole website admin authority, report resolution and deletion audits. Never let a Feed target fall through to the message path. Audit actor/source/reason/report bindings must derive from locked server rows. Existing USER/MESSAGE and E2EE consent/custody behavior must stay intact.
- DATA's Feed DTOs have strict public author/game projections; do not send email, Discord identity, internal role flags or private profile/notes. Parent source bodies and post images must stay masked/denied after deletion through list, direct URLs, reload and caches. Use actual no-store/private responses where actor block state affects visibility.
- Add real API/PG/Redis/object-store tests for guest reads/write denial, other-author edits, current banned/stale session, forged helper/admin, block filters, root-depth/cross-post/races, upload purpose/ownership/expiry/size/signature/pixel/sweep, delete direct-asset denial, report/audit and retry counts. No mocks as a substitute for those boundaries. Actual UI/mockup03/headed screenshots belong to T38-FEED-FE after BE PASS and backup.

No Feed push/email/realtime events are introduced. Voice/live/PWA/email and the 1,000 concurrent call/live target remain unchanged future acceptance gates.
